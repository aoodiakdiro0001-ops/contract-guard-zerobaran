## نظرة عامة

يتبع النظام معمارية **طبقات متعددة (Layered Architecture)** مع فصل واضح للمسؤوليات. كل طبقة مستقلة وقابلة للاستبدال، مما يسمح بتطوير وصيانة كل جزء دون التأثير على البقية.

## الطبقة 1: الاستخراج والقراءة القانونية

### المسؤولية
استلام ملف العقد الخام وتحويله إلى بنود قانونية منظمة.

### المكونات
| المكوّن | الملف | الدور |
|---------|------|------|
| `PDFParser` | `parsers/pdf_parser.py` | استخراج النص من PDF عبر PyMuPDF |
| `DocxParser` | `parsers/docx_parser.py` | استخراج النص من Word عبر python-docx |
| `ContractSegmenter` | `parsers/contract_segmenter.py` | تقسيم النص إلى بنود مرقمة + كشف أولي للمخاطر |

### نمط البيانات (Data Model)
```python
@dataclass
class Clause:
    number: str        # "1" أو "4.2"
    title: str         # "التعريفات"
    text: str          # نص البند الكامل
    section: str       # القسم الذي ينتمي إليه
    index: int         # الترتيب
    word_count: int    # عدد الكلمات
    risk_flags: List[str]  # إشارات خطر أولية
```

### خوارزمية التقسيم
1. تنظيف النص (تطبيع الأسطر الجديدة)
2. محاولة النمط العربي: `المادة X` / `البند X` / `الفقرة X`
3. احتياط: النمط الرقمي `1.` / `2.` / `3)`
4. احتياط أخير: التقسيم حسب الفقرات المزدوجة

## الطبقة 2: العقل القانوني الذكي

### المسؤولية
تحليل كل بند قانوني، تقييم المخاطر، اقتراح صياغات بديلة.

### المكونات
| المكوّن | الملف | الدور |
|---------|------|------|
| `GeminiAnalyzer` | `ai/gemini_analyzer.py` | محرك Google Gemini (الافتراضي) |
| `GroqAnalyzer` | `ai/groq_analyzer.py` | محرك Groq البديل (أسرع) |
| `LegalPrompts` | `ai/prompts.py` | مكتبة البروتوكولات القانونية |

### استراتيجية اختيار المحرك
```python
if ai_provider == "gemini" and is_gemini_ready:
    use GeminiAnalyzer()
elif ai_provider == "groq" and is_groq_ready:
    use GroqAnalyzer()
else:
    use any available provider
```

### نمط بروتوكول التحليل
```text
النظام: "أنت خبير قانوني بارز..."
المستخدم: "حلّل البند التالي... أرجع JSON بالشكل..."
الناتج: {
  "risk_level": "عالية|متوسطة|منخفضة|آمن",
  "risk_summary": "...",
  "risk_factors": ["...", "..."],
  "recommendation": "...",
  "alternative_drafting": "..."
}
```

### مستويات الصرامة
- **lenient:** لا يصرّ إلا للخطر الواضح
- **balanced:** موضوعي متوازن (افتراضي)
- **strict:** يعتبر أي غموض خطراً جسيماً

## الطبقة 3: الأرشفة وقاعدة البيانات

### المسؤولية
حفظ العقود، التقارير، والمواعيد النهائية بشكل دائم.

### المخطط (ERD)
```
contracts (1) ──── (N) risk_reports
    │
    └──── (N) deadlines
```

### الجداول
1. **contracts**: العقد (id, title, source_file, raw_text, metadata, status)
2. **risk_reports**: تقرير المخاطر (contract_id, clauses_analyzed, overall_verdict, full_report)
3. **deadlines**: المواعيد النهائية (contract_id, title, due_date, notified)

### حالات العقد
- `قيد المراجعة` (افتراضي)
- `مقبولة`
- `تحتاج تعديل`
- `مرفوضة`
- `موقعة`

## الطبقة 4: التسليم والتحكم

### المسؤولية
إيصال التقارير للمستخدم عبر القنوات المناسبة.

### القنوات
1. **Telegram Bot** (`delivery/telegram_bot.py`):
   - استقبال ملفات ونصوص العقود
   - إرسال التقارير المنسّقة
   - أوامر: `/start`, `/status`, `/help`

2. **Streamlit Dashboard** (`dashboard/streamlit_app.py`):
   - رفع الملفات
   - عرض التقارير التفاعلية
   - توليد المسودات
   - إدارة الأرشيف

3. **CLI** (`scripts/run_analysis.py`):
   - `file <path>`: تحليل ملف
   - `text --text-file <path>`: تحليل نص
   - `--check-deadlines`: فحص المواعيد
   - `--check-new`: فحص عقود جديدة

### منسّق التقارير (`ReportFormatter`)
يحوّل التقرير إلى ثلاث صيغ:
- `to_telegram_message()`: رسالة تليجرام (≤ 4096 حرف)
- `to_markdown_report()`: تقرير Markdown كامل
- `to_short_summary()`: ملخص سطر واحد

## مبادئ التصميم

1. **التبعية للتجريد (Dependency Inversion)**: المحركات (Gemini/Groq) قابلة للاستبدال
2. **المسؤولية الواحدة (Single Responsibility)**: كل طبقة تخدم هدفاً واحداً
3. **التحمل الأخطائي (Fault Tolerance)**: كل طبقة تعمل باستقلالية، فشل طبقة لا يوقف البقية
4. **الإعداد الصفري للبدء**: يعمل بـ 0 تكلفة وحد أدنى من الإعداد
5. **السرية أولاً**: البيانات تبقى في بيئة المستخدم
